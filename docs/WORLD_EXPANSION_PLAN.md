## 2. Координаты: логическая сетка отдельно от картинки

В модели хранить целочисленную клетку `Vector2i(u, v)`. Экранные координаты,
масштаб камеры, пиксельные отступы интерфейса и Node не попадают в данные карты.
Отрицательные координаты допустимы: ферма сможет расширяться в любую сторону.

Проекцию задаёт `IsoGrid` с ресурсом `GridMetrics`:

```text
x = origin.x + (u - v) * tile_width / 2
y = origin.y + (u + v) * tile_height / 2

u = (x - origin.x) / tile_width + (y - origin.y) / tile_height
v = (y - origin.y) / tile_height - (x - origin.x) / tile_width
```

Для визуальной совместимости сначала использовать `tile_width = 320`,
`tile_height = 256`: базисы `(160, 128)` и `(-160, 128)` точно соответствуют
текущему расположению. У стартового набора `u = col`, `v = row`,
`origin = (0, -256)`. Это сохраняет принятый наклон/пропорции стилизованной
изометрической сетки; переходить на другую пропорцию только ради классических
2:1 сейчас не нужно. Размер клетки и фактические границы нарисованной почвы различаются.

Функции `cell_to_world()`, `world_to_cell_fractional()` и `world_to_cell()`
должны иметь один источник реализации и тесты обратного преобразования.
Для выбора объекта округлённая клетка даёт кандидатов, а не окончательный ответ:
учитываются footprint, форма выбора и экранный размер touch target.

Карта делится на логические чанки **16×16 клеток** как начальный параметр для
профилирования. Чанк не равен открываемой территории: регион может содержать несколько
чанков или их части. Отрицательные координаты считать через floor, а не усечение:
клетка `(-1, 0)` принадлежит чанку `(-1, 0)` и локальной клетке `(15, 0)`.

## 3. Данные: определения и изменяемое состояние

| Тип | Что хранит |
| --- | --- |
| `WorldDefinition` / `RegionDefinition` | Идентификатор мира, метрики сетки, стартовые объекты, границы территорий, biome_id и связи соседства; неизменяемые локальные Resources |
| `WorldState` / `ChunkState` | Открытые регионы, изменения ландшафта и реестр размещённых объектов; динамические коллекции |
| `PlacedObjectRecord` | instance_id, definition_id, тип, anchor_cell, поворот; общая запись размещения |
| `PlotState` | Стабильный plot_id/ссылка на размещённую грядку и ссылка на текущую культуру; не владеет камерой или графикой |
| `CropState` | plant_definition_id, planted_at_utc, ready_at_utc, cycle_id, признак получения награды; стадия/готовность выводятся из времени |
| `PlantDefinition` | Локализационные ключи, стоимость, время, награда, ссылка/ключ визуального представления |
| `BuildingDefinition` / `BuildingState` | Footprint/правила размещения отдельно от изменяемых данных конкретной постройки; производственные механики добавятся позже |
| Определения дорог, деревьев, декораций | Footprint, слой размещения, графика и свойства; необязательное специфическое состояние хранится отдельно |
| `PlayerState` | Монеты, статистика, открытые возможности; не содержит список из девяти обязательных слотов |

Девять грядок остаются **содержимым стартового региона**. Число 9 не входит в
экономику, валидатор любого сохранения, цикл роста или ограничения команд.
Стартовый тест вправе ожидать девять; общий валидатор проверяет уникальность,
ссылки, допустимость размещения и значения, а не фиксированный размер массива.

`instance_id` не зависит от индекса в массиве или текущей позиции. Перемещение
будущей постройки не меняет её ID. Для стартовых объектов допустимы стабильные
идентификаторы из определения региона; новые объекты получают уникальный локальный ID
один раз. `definition_id` и `species_id` никогда не заменяются переведённым названием.

Публичный интерфейс логики:

```text
PlantCommand(plot_id, plant_definition_id, expected_cycle_id)
HarvestCommand(plot_id, expected_cycle_id)
PlacementService.can_place(definition_id, anchor_cell, rotation)
WorldQuery.get_plot(plot_id)
WorldQuery.objects_in_world_rect(rect)
```

HUD не меняет баланс напрямую; видимая сцена не определяет существование объекта.
Удаление представления чанка не удаляет растение из модели и сохранения.

## 4. Размещение объектов

Footprint — набор логических клеток относительно anchor_cell, а не размер PNG.
Для прямоугольного здания 2×3 проверяются все шесть клеток; поворот преобразует
footprint дискретно на 90°. У грядки стартового размера footprint 1×1.

Разделить слои занятости:

- Terrain: базовая земля, вода, пригодность для строительства/посадки.
- GroundOverlay: дороги и дорожки с явными правилами совместимости.
- SolidObject: грядки, деревья, постройки, крупные декорации.

Правила задаются определением объекта. Дорога не должна автоматически разрешаться
под любым зданием; совместимость и точки входа описываются явно. Визуальный навес
дерева не обязан занимать все клетки под своей картинкой.

PlacementService проверяет доступность всех клеток региона, тип поверхности,
занятость, поворот и разрешённые сочетания слоёв. Экономика, оплата открытия региона
и создание объекта впоследствии должны составлять одну команду/транзакцию.
До этапа 1 нужен общий контракт, проверка footprint и индекс занятости; полноценный
строительный редактор, дороги, производство и покупка территорий сейчас не нужны.

Для объекта через границу чанков хранить одну запись у владельца anchor_cell.
Пересекаемые чанки содержат ссылки/индекс, а не копии состояния. Стриминг должен
учитывать полный visual_bounds и footprint: высокое дерево или большое здание может
быть видно, даже если его anchor находится за пределами экрана.

## 5. Камера и жесты

Предлагаемое дерево сцены:

```text
FarmRoot (Node2D)
  WorldView
    TerrainChunks (TileMapLayer / кешированные слои)
    GroundOverlays
    WorldObjects (Node2D, y_sort_enabled = true)
      видимые грядки / растения / деревья / здания
    AmbientEffects
  CameraRig
    Camera2D
  HUD (CanvasLayer)
    текущий интерфейс, локализованные панели и модальные окна
```

Объекты разных чанков должны попадать в общий порядок YSort по опорной точке у земли.
Отдельный YSort внутри каждого чанка приведёт к неверному перекрытию на границах.
Абсолютный `z_index = world_y` для большой карты непригоден; у CanvasItem ограничен
диапазон z, а HUD должен оставаться независимым от глубины мира.

CameraRig хранит фокус и zoom. Текущее кадрирование стартового участка переносится
с `world.scale/world.position` на камеру без изменения масштаба самого мира.
Доступный прямоугольник сада рассчитывается с учётом HUD и safe area. Изменение
высоты перевода или панели не должно сбрасывать пользовательский pan/zoom:
автокадрирование допускается при первом показе, явном центрировании и необходимом
изменении viewport, с сохранением выбранного мирового фокуса.

`WorldInputRouter` отделяет жесты от команд:

1. UI получает события первым; касание, начавшееся на UI, принадлежит UI до отпускания.
2. Первый палец создаёт pending tap. После сдвига примерно на 8 логических px это pan.
3. Второй палец в зоне мира отменяет tap; pinch изменяет масштаб относительно центра
   двух пальцев, сохраняя мировую точку под этим центром без скачка.
4. Команда выбора/посадки выполняется на отпускании только подтверждённого одиночного tap.
   После pinch нельзя случайно выбрать грядку оставшимся пальцем.
5. Desktop: click/drag и колесо; локализованные кнопки zoom/центрирования размером ≥48px
   дают альтернативу жестам и удобны для проверки.

Начальные пределы zoom — настраиваемые, не экономические ограничения. Камеру
ограничивать навигационной областью открытых регионов с запасом под края окружения;
для маленького стартового участка корректно центрировать ось, если мир меньше viewport.
В reduced motion отключить инерционное скольжение и лишние плавные перелёты.

**Важный UX-компромисс:** при сильном уменьшении нельзя гарантировать каждой плотной
грядке отдельную непересекающуюся область 48×48. В обзорном масштабе tap должен
приближать соответствующий участок или открывать понятный выбор. Непосредственная
работа с грядками включается при достаточном масштабе. В рабочем масштабе сохраняем
минимум 48×48; при пересечении расширенных областей выбираем ближайший экранный центр,
при равенстве — стабильный ID. Pinch и pan никогда не сажают и не собирают растение.

## 6. Сохранение большого мира

Настройки языка и reduced motion остаются в `settings_v1.cfg` и не сбрасывают ферму.
Игровое сохранение имеет версию схемы, world/content version и локальный save_id.
Коллекции сериализуются с ID и ссылками: player, unlocked_regions, placed_objects,
plot_states, crop_states, terrain_deltas. Координаты — целые логические клетки.
Статический неизменённый ландшафт берётся из локальных определений мира; сохраняются
только отличия игрока, а не тысячи неизменённых тайлов и не дерево Node.

Стадия и ready могут сохраняться как кеш для требований этапа 1, но при загрузке и
сборе пересчитываются по UTC. Награда проверяется по plot_id + cycle_id и отмечается
синхронно до анимации. Изменение монет и культуры всегда входит в одно сохранение.

### Что делать до этапа 1

Ввести интерфейс `SnapshotStore.commit/load/recover` и кодек без ограничений 3×3.
Для малого стартового участка допустима один атомарный JSON-снимок + last-good backup:
это проще проверить на раннем этапе. Конкретный формат файла скрыт от GameState.
Не вводить SQLite, сетевую базу или несколько частично согласованных JSON просто
ради будущей большой карты. Длительность записи измерить на синтетических наборах;
не обещать отсутствие задержек без измерений.

### Как перейти к большой ферме без переписывания игровой логики

Следующая реализация того же SnapshotStore: неизменяемые файлы чанков/состояния
игрока и маленький manifest, который ссылается на согласованный снимок.

1. Собрать кандидат транзакции с новой generation; заблокировать повтор этой команды.
2. Записать временные файлы игрока и изменённых чанков, закрыть/flush, проверить
   целостность, переименовать в уникальные неизменяемые имена. Неизменённые файлы переиспользуются.
3. Записать новый manifest со ссылками/контрольными суммами. Замена manifest — точка фиксации.
4. Только после успешной фиксации применить результат и запустить эффекты награды.
5. При загрузке проверить **весь набор ссылок**; при повреждении восстановить целиком
   предыдущий согласованный manifest, а не независимо выбирать «самый свежий» чанк.
6. Удалять осиротевшие файлы лишь после фиксации и с сохранением файлов обоих живых
   manifests. Контролировать расход диска и ошибки записи.

Иначе легко получить новый баланс из одного файла и старую готовую культуру из
другого — источник повторной награды. Future schema не перезаписывать старым кодом.
При повреждении обеих копий показывать восстановление/подтверждённый сброс и сохранять
исходные файлы. На мобильных устройствах отдельно проверять прерывание записи и
поведение rename/flush; абсолютную защиту от потери питания заранее не заявлять.

Данные карты, индекс, кодек и игровой API должны поддерживать шардирование с самого
начала, но реализовывать сложный многофайловый протокол до маленького рабочего цикла
не требуется. Размер чанка и порог перехода выбрать по профилированию, а не по догадке.

## 7. Отображение и логика вне экрана

- Terrain: TileMapLayer Godot 4.6.3 или кешированная геометрия чанка; не Node на клетку.
- SpatialIndex и ChunkManager определяют видимые объекты по обратной проекции viewport
  с запасом на высокие спрайты, соседние клетки и быстрый pan.
- Создавать представления только в видимой области и небольшом запасе. Подгружать
  постепенно, чтобы открытие региона не породило сотни Node за один кадр.
- Выгружать представления с небольшим гистерезисом; модель и данные сохранения живут
  независимо. Тяжёлые ресурсы подгружать асинхронно при необходимости.
- Статические фоновые элементы не перерисовываются из-за движения одной бабочки.
  Атласы/пакетная отрисовка и MultiMeshInstance2D для однотипной травы возможны позже
  по результатам профиля; текущую оригинальную векторную графику не выбрасывать.
- Пыльца, бабочки, цветочные колебания имеют общий бюджет на viewport, не на каждый
  чанк. Иначе их количество вырастет вместе с размером фермы.
- Рост основан на timestamps, не на таймере каждого растения. Один секундный тик
  обновляет видимые/выбранные растения; вне экрана стадия вычисляется по запросу.
- Для глобальных индикаторов готовности при необходимости добавить индекс ready_at
  со ссылкой на cycle_id, а не обход всей фермы каждый кадр. Производственные здания
  используют отдельные системы, без привязки к PlantView.
- Цель 60 FPS на среднем Android остаётся целью, а не результатом desktop-тестов.
  Сначала измерить видимые объекты, draw calls, время подгрузки, RAM и сохранение.

Мир может быть конечным, но расширяемым набором регионов. Бесконечная генерация,
сервер и плавающий origin до появления реальной необходимости не нужны. Целочисленные
клетки и граница между моделью/рендером позволят добавить rebase представления позже,
если дальние координаты действительно начнут вызывать потерю точности.

| D. InputRouter + spatial query | Tap/drag/pinch не конфликтуют, точные цели в рабочем масштабе | Края клеток, равные расстояния, pinch не вызывает действие, UI не двигает камеру |
| E. Версионированный SnapshotStore | Общие коллекции и стабильные ID без размера 9 | Round-trip, несуществующая ссылка, дубликат ID, повреждение/backup, сбой записи |
| F. Возобновление этапа 1 | Шесть уже заказанных растений, посадка/рост/сбор поверх этого API | Экономика, offline, повторный сбор, сохранения и скриншоты из задания этапа 1 |

Полный редактор построек, открытие территорий, новые биомы и тысячи отрисованных
объектов не входят в A–E. Синтетические данные нужны для тестов контрактов, а не для
добавления большой карты в игру. После этого этап 1 остаётся на стартовом участке,
но та же команда посадки работает на любой корректной открытой грядке.

## 9. Риски и критерии готовности

1. Потеря принятой композиции при переносе под камеру: сравнить изображения до/после,
   сохранить палитру, масштаб и стартовое кадрирование; не утверждать битовую идентичность.
2. Случайная посадка при pan/pinch: действия только по подтверждённому tap, тесты
   жизненного цикла нескольких пальцев и обязательная ручная проверка на устройствах.
3. Слишком мелкие объекты при zoom-out: обзорный режим и переход к рабочему масштабу,
   а не обещание физически невозможных непересекающихся целей 48px на любой плотности.
4. Неправильное перекрытие больших объектов/разных чанков: общая сортировка по опорным
   точкам; сложные высокие здания могут потребовать частей для корректной окклюзии.
5. Дубли объектов/награды и смешанные сохранения: один владелец ID, целые транзакции,
   цикл культуры, согласованная генерация и тесты прерывания записи.
6. Долгие кадры/запись при большой ферме: ленивые представления, пространственный индекс,
   бюджет стриминга и измерения; фоновые сохранения вводить с блокировкой/подтверждением
   транзакций, не с бесконтрольными параллельными изменениями.
7. Излишнее усложнение до первой посадки: сейчас только контракты, стартовый регион,
   камера/ввод, размещение и маленькое надёжное сохранение; контент расширения позже.

**Граница текущей задачи:** документ и аудит. Рабочий код остаётся этапом 0.5.
Реализацию шагов A–E и возобновление этапа 1 выполнять после согласования этого плана.
